# 2026-11-08

## 平台架构分析（agentscope-ruoyi/platform）
- 研发运维智能体平台，8 个 Maven 模块：domain / infra / governance / executor / tools / runtime / gateway / spec-checks。依赖严格单向（A1 规则，ArchitectureRulesTest），domain 零框架；tools 经 domain 端口依赖 governance/executor 实现（依赖倒置，已 grep 核实零跨层 import）。
- 核心设计：动作契约 + 仓库内配方（方案 D）替代 Jenkins。决策文档 `docs/CICD方案替代与自创-决策-v1.md`，执行器规约 `docs/规约-流水线执行器-v1.0.md`。
- 方案 D 落地代码：`ActionSpec`（argv 数组非 shell 字符串）、`RecipeActionResolver`（actions.yml→Taskfile→Makefile→内置默认 4 源解析）、`ActionRunner`/`AbstractActionRunner`（确定性执行骨架）、`ActionService` 门禁（L2 非生产直跑 / L3 request→confirm→apply，令牌绑 planHash）。
- 已指出方案 D 的缺点（规约 vs 实现落差，均有代码证据）：① 编排层（多 stage 串联）缺失，PipelineEngine 为 Noop，只建模 5 个离散动作；② make/task 路径安全边界失效（argv 白名单与 E-202 不覆盖 make/task，内部 shell 平台零可见）；③ 无 Docker 回退宿主执行，S1-S7 沙箱不变量落空；④ 审计缺 commit（ActionSource 只有 kind+ref，无 commit 字段，验收#2 未实现）；⑤ 错误码缩水（ProcessExecutor 仅 E-101/209/302/303，E-401 产物缺失不失败，E-211/212/202 平台校验全无）；⑥ PipelineSpec（规约主角）与 ActionSpec（代码主角）术语不一致，双执行入口并存；⑦ 动作参数枚举（profile/mode）未落地；⑧ 配方三源歧义 + 动作上限 8 表达力受限。
- 评价：设计哲学（确定性中间表示、人写命令模型选动作）正确优雅；但实现与规约落差大，目前是"触发+治理+极简执行"骨架，距"替代 Jenkins 执行器内核"还差错误分类/产物校验/env 白名单/redactor/6 态/落库。
