# 流水线自动部署：环境适配修复方案与实现 v1

> 适用代码：`platform/`（agent-infra / agent-executor / agent-tools / agent-runtime / agent-gateway）
> 关联文档：《规约-流水线执行器-v1.0.md》《发布编排与平台部署器-v1.md》《环境变量与环境模板设计-v2.md》《流水线工作台-使用指南-v1.md》
> 结论：部署失败率高不是"环境变数太多"，而是**脚手架把单机 Java 假设写死**：缺 Node 工具链、只认根 Dockerfile、健康检查固定 `127.0.0.1:port/200`、固化脚本固定 docker/8080、未知环境静默落 test、`POSTGRES_*` 被当成 MySQL。本方案把"环境事实"变成**可探测、可声明、可诊断**的数据，引擎只执行、不猜测。

---

## 1. 根因清单（代码定位）

| # | 现象 | 根因（修复前） |
|---|------|----------------|
| 1 | Java + Vue 项目 frontend stage 永远失败 | `RecipeScaffolder` 生成的 frontend stage 不带 `image`，落回默认 `maven:3.9-eclipse-temurin-21`，镜像内没有 Node |
| 2 | 前后端同仓、Dockerfile 不在根目录 → E-501 | 只检查仓库根 `Dockerfile`；Java+Node 无根 Dockerfile 仍保留 DOCKER 目标 |
| 3 | SERVER 目标健康检查永远失败 | 生成的 health URL 固定 `http://127.0.0.1:<port>`，且只接受 `200`；非 2xx 端点（201/204/302）误判 |
| 4 | 宿主/服务器环境 replay 报 E-504 | `DeployTools.saveRecipe` 固定渲染 `docker(8080)` |
| 5 | 有 `mvnw`/`gradlew` 仍用全局 mvn/gradle；pnpm 未 enable | 命令硬编码；安装命令无 `corepack` |
| 6 | 环境名拼错静默跑 test | `normalizeEnv` 把未知值回落到 test |
| 7 | 必填变量漏检 | 只扫 `.env.example` 少数固定位置 |
| 8 | PostgreSQL 项目自动起了 MySQL | `kindOfKey` 把 `POSTGRES_*` 映射成 `mysql` |
| 9 | 规则识别失败时不会请 agent 补定义 | 仅 `stack=UNKNOWN` 才走 agent 兜底 |
| 10 | 部署失败后 agent 反复重试仍失败 | 恢复提示让 agent 直接 `deploy_run`，但该工具要求人工确认的 `binding_id` |
| 11 | 固化脚本回放不了/触发错流水线 | `DeployController` 固定 `PIPELINE="release"` |
| 12 | dev/test 迭代被 E-508 拦住 | "部署配置必须与默认分支一致"对所有环境生效 |

## 2. 修复原则

1. **先探测、再声明、最后才是默认值**：`平台默认 → 项目声明（ci/pipeline.yml、ci/actions.yml）→ 环境模板/覆盖 → 运行时探测`。
2. **能力不匹配就明确降级或阻塞**：不再生成"必然 E-501"的定义，也不静默换环境。
3. **健康检查按部署目标取地址**：DOCKER/HOST 用本机映射端口，SERVER 用部署器返回的真实 endpoint。
4. **安全边界不放松**：agent 仍只能选白名单动作，不能写 shell；变更仍受确认令牌约束。

## 3. 关键契约变更

### 3.1 stage 工具链镜像

`ci/pipeline.yml` 的 action stage 支持 `image`：

```yaml
stages:
  - id: frontend
    type: action
    action: frontend_build
    runner: container
    image: node:20-bookworm        # 前端构建必须用 Node 镜像
    workdir: ruoyi-ui
```

- `image` 为空 → 使用平台默认沙箱镜像（Java 场景）。
- 宿主模式（`agent.sandbox.mode=process`）忽略 `image`，工具链由宿主机提供。

### 3.2 健康检查

```yaml
- id: health
  type: health
  url: http://127.0.0.1:8080/actuator/health
  expected: 2xx        # 也接受具体码：200 / 201 ...
```

- `expected: 2xx`（内部表示 0）表示任意 2xx。
- **SERVER 目标**：执行期把 URL 的 scheme/host/port 替换为部署器返回的真实 endpoint，只保留 path。避免远端服务器上探 `127.0.0.1`。

### 3.3 部署目标与 Dockerfile

Dockerfile 探测顺序：仓库根 → `backend/` → `frontend/` → `deploy/` → `docker/`。

- 找到即认为 DOCKER 可行，镜像命令带 `-f <dockerfile>`，构建上下文取 Dockerfile 所在目录。
- 请求 DOCKER 但无 Dockerfile：
  - 纯 Java → 自动降级 HOST（已有行为）；
  - Java + Node → 降级 HOST，并明确提示"前端静态产物不由平台托管"；
  - 无 Java/Node → 保留 blocker（不生成必然失败的目标）。
- `Dockerfile` 内已有 `mvn/npm` 编译步骤时，不再重复生成构建 stage。

### 3.4 环境名

`dev / test / prod` 之外的环境名 **fail-fast**（参数错误 E-201 风格），不再静默落到 test。空值仍默认 test。

### 3.5 环境变量探测（只取名字）

扫描并合并：

- `.env.example` / `.env.sample` / `.env.template` / `.env`（根目录与一层子目录、`docker/`）；
- `application*.yml/properties` 中的 `${VAR}`、`${VAR:default}`；
- `docker-compose*.yml` 中的 `${VAR}`（无默认值的视为必填）；
- `Dockerfile` / `*.Dockerfile` 的 `ENV KEY=...`。

只把变量名写入 `deploy.env-required`，值仍归「设置 → 项目环境」。

### 3.6 中间件识别

| 变量前缀 | 中间件 |
|----------|--------|
| `POSTGRES*` | postgres |
| `MYSQL*` / `MARIADB*` | mysql |
| `REDIS*` | redis |
| `RABBITMQ*` | rabbitmq |
| `MONGO*` | mongo |
| `MINIO*` | minio |
| `DB_*`（无法判定） | mysql（保留兼容，日志提示显式声明） |

## 6. 暂未引入的独立 profile 文件

当前"项目层"仍由仓库里的 `ci/pipeline.yml` + `ci/actions.yml` 承担（已有 `deploy.target/port/healthPath/env-required` 与 stage `image`），
没有额外引入 `deploy/profile.yml`。原因是：再增加一层配置文件会放大"页面一套、执行一套"的风险，
先把 stage 镜像、构建命令、健康检查、环境发现这些**真实失败点**收敛到现有契约；
等出现"同仓库多环境差异配置"的真实需求，再在同一解析器上扩展 profile 层。

## 7. 验收

- Java + Vue（pnpm，前端子目录）导入后生成的 `ci/pipeline.yml`：frontend stage 带 `image: node:20-bookworm`，install 命令含 `corepack enable`。
- 无 Dockerfile 的 Java+Node：目标降级 HOST 并给出诊断，而不是 E-501。
- SERVER 目标：健康检查访问部署器返回的 endpoint，2xx 通过。
- `env=staging`：触发前直接报参数错误，不落 test。
- PostgreSQL 项目：自动创建的中间件是 postgres，不是 mysql。
- dev/test 不受 E-508 限制；prod 仍要求 `ci/pipeline.yml` 与默认分支一致。
- `mvn -q test`（受影响模块）通过。
