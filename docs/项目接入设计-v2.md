# 项目接入设计：引入项目到平台（v2 · 直接引用本地目录 + git 工作树 · 含前端设计）

> 日期：2026-11-08 ｜ 现行方案（v1 已过时删除） ｜ 前置：[多项目托管设计 v4](多项目托管设计-v4.md)
> 需求变更（用户决策）：
> 1. **本地项目不再复制**——直接填写本地目录、平台原地读取；
> 2. **git clone 也落到指定目录**（clone 与本地目录是同一套"仓库存储"概念）；
> 3. **本地与远程要能对比**（本地改动 vs 远端新增）；
> 4. **读取不同的工作树**（一次检出，多份并行工作副本，互不覆盖）。

---

## 0. 一句话结论

**项目 = 一个 git 仓库（bare 仓库做对象库）+ N 个 git worktree（本地原目录可就地成为第一个 worktree）+ 平台管理的工作树（构建/发布用）。
本地导入 = 把用户目录"收编"为平台托管仓库；远程 clone = clone bare 到工作区；
对比 = 本地 worktree 的 HEAD/工作区状态 vs 远端 refs；
多检出 = `git worktree add`，每次构建用独立 worktree，不污染任何人的工作副本。**

## 1. 为什么从"复制"改为"就地引用 + worktree"（v1→v2 变更理由）

| v1 方案（复制到工作区） | 问题 | v2 方案（就地引用 + worktree） |
|---|---|---|
| 把用户目录复制到 `workspaces/<id>/repo` | 双份磁盘；用户在原目录的改动**不同步**，构建永远用旧代码 | 用户目录就地成为托管仓库的一个 **worktree**，改动实时可见 |
| 复制时丢 git 历史风险 / 权限混乱 | 复制 `.git` 慢且易错 | 不复制 `.git`——用 `git worktree` 机制，对象库只有一个 |
| 无本地/远程对比能力 | 用户改了什么、远端有什么新提交，平台说不上来 | 一等公民功能：**diff 摘要工具**（§4） |
| 每次构建 clone 到 runs/ | 重复 clone，慢 | **worktree add（毫秒级）**，同一对象库零重复存储 |

核心 git 机制（都是本地操作，无网络）：

```
bare 仓库（对象库，只有一个）:  workspaces/<id>/git          ← 所有提交对象都在这
worktree（工作副本，可以有 N 个）:
  ├── 用户本地原目录        （importLocal 时接入，用户继续在里面开发）
  ├── workspaces/<id>/wt-build/<runId>   ← 每次流水线构建一个，用完可删
  └── workspaces/<id>/wt-verify/         ← 配方自检/agent 代码检索用（常驻）
```

`git worktree add <path> <commit>` 只创建指向 bare 仓库的轻量工作副本（几十 ms、几乎零额外磁盘），
删除 `git worktree remove` 同样干净——这是"读取不同的工作树"的底层支撑。

## 2. 两种来源，一个存储模型

### 2.1 来源 A：本地目录导入（主路径，用户决策）

**接入三步**：
1. 填本地路径（如 `E:\CODE\ruoyi-vue-plus`）
2. 平台校验：目录存在、含 `.git`（或可 `git init`）、git 可用
3. 平台执行"收编"（不动用户目录内容）：

```bash
# 1) 建平台 bare 仓库
git init --bare workspaces/AGT/git

# 2) 用户目录作为第一个 worktree 挂进平台仓库
#    （用户目录必须与 bare 仓库关联，才能 fetch/push 对象）
git -C <用户目录> remote add agent <bare仓库路径>
git -C <用户目录> push agent HEAD                       # 对象进 bare
git -C <bare仓库路径> worktree add <用户目录> <HEAD>     # 原目录登记为 worktree
```

**收编语义（重要）**：
- 用户目录的 `.git` 仍指向它原来的 remote（gitee 等）——用户继续正常 pull/push 自己的项目
- 平台通过 bare 仓库 + `fetch from 用户目录` 读到本地最新提交
- 用户在原目录正常开发，平台每次构建前 `fetch` 一次用户目录（本地操作，快）即可拿到最新
- **平台永远不改用户目录**（只读 + fetch）；构建/写操作全部走平台自己的 worktree

**无 `.git` 的纯目录**：先在**平台侧**建 bare + worktree 挂到用户目录？
——不行，worktree 必须属于同一仓库。改用：
```bash
git init <用户目录>            # 只加 .git，不动文件
git -C <用户目录> add -A && git -C <用户目录> commit -m "intake: initial"
# 之后同上（push 到平台 bare）
```
向导里明确告知"该目录将被 git init"，让用户确认。

### 2.2 来源 B：远程 clone（Gitee/GitLab）

```bash
git clone --bare <url> workspaces/<id>/git      # bare，省磁盘（不检出工作文件）
git -C workspaces/<id>/git worktree add wt-verify HEAD --detach   # 常驻自检用
```

- `--bare`：对象库不占双份磁盘
- token 只用于 clone/fetch 命令行，不落盘（同 v1 P1 方案）
- 用户后续如果也想在本地开发该项目：`git clone <url> <本地路径>`（用户自己的事，与平台无关）；
  或用平台的"挂载本地 worktree"功能把该目录收编为第二个 worktree（走 §2.1 收编流程）

### 2.3 统一存储模型

```
${AGENT_WORKSPACE_ROOT}/
├── AGT/                          # <projectId>
│   ├── git/                      # bare 仓库（对象库，唯一）
│   ├── worktrees/                # 平台管理的 worktree
│   │   ├── wt-verify/            # 常驻：配方自检、agent 代码检索
│   │   └── wt-build-<runId>/     # 构建：流水线每次运行一个，终态后清理
│   └── _history/                 # 构建历史 YAML（RunHistoryStore，不变）
└── SHOP/
    └── ...
```

**与现有代码的兼容**：
- `BuiltInPipelineEngine.checkout()` 现在是 `git clone <repoDir> → runs/<runId>`——
  改为 `git worktree add`（P0 改造点，见 §6）
- `RecipeActionResolver.resolveCommit()` 读 `<repoRoot>/.git/HEAD`——worktree 有自己的
  `.git` 文件（内容是 `gitdir: ...`），`HEAD` 解析要适配（git 命令 `rev-parse HEAD` 替代手读文件）
- `InMemoryProjectRepository`/`ProjectsProperties` 加 `source` 字段：
  `LOCAL`（含 localPath）/ `REMOTE`（含 repoUrl）

## 3. 本地 vs 远程对比（新增能力）

### 3.1 对比什么

| 对比维度 | 命令 | 输出 |
|---|---|---|
| **本地领先远端**（待推送提交） | `git log --oneline <remoteBranch>..<localBranch>` | 提交列表 |
| **远端领先本地**（待拉取提交） | `git log --oneline <localBranch>..<remoteBranch>` | 提交列表 |
| **分叉**（两边都有新提交） | `git log --left-right --oneline <local>...<remote>` | 双侧提交 |
| **本地未提交改动** | `git -C <用户目录> status --porcelain` | 修改/新增/删除文件列表 |
| **文件级 diff 摘要** | `git diff --stat <local>..<remote>` | ±行数统计 |

### 3.2 API 设计

| 端点 | 说明 |
|---|---|
| `GET /api/v1/projects/{id}/git/status` | 本地 worktree 状态：当前分支/HEAD、未提交改动数、领先/落后远端提交数 |
| `GET /api/v1/projects/{id}/git/diff?against=remote\|local` | 分支级 diff 摘要（提交列表 + stat） |
| `POST /api/v1/projects/{id}/git/sync` | 从本地目录（LOCAL 来源）fetch 到 bare / 从 remote（REMOTE 来源）fetch |

**agent 工具（供 LLM 调用，只读）**：
- `git_project_status`：当前项目本地/远端差异摘要（"我的项目有没有没推送的提交？"）
- `git_project_diff`：本地 vs 远端的文件级差异（±N 行、涉及文件列表）

**安全边界**：对比全部只读；`sync` 只做 fetch（从本地目录或远端拉对象进 bare），
**平台绝不 push 到用户目录或远端**——推送永远是用户自己的动作。

### 3.3 LOCAL 来源的对比语义

LOCAL 项目的"远端"有两个：
1. **用户目录自己的 origin**（如 gitee）——平台不碰，但可以在 status 里**只读展示**它落后的提交
   （`git -C <用户目录> fetch origin --dry-run` 不落对象，或直接读 `origin` refs 对比）
2. **平台 bare 仓库**（agent remote）——平台构建用的就是它

状态报告把两者都列出：
```json
{"localHead": "abc1234", "branch": "main",
 "agentRemote": {"ahead": 0, "behind": 0},          // 本地 vs 平台 bare
 "userOrigin": {"ahead": 2, "behind": 0, "note": "仅展示，平台不推送"}}
```

## 4. 多工作树（worktree）管理

### 4.1 用途与生命周期

| worktree | 生命周期 | 用途 |
|---|---|---|
| `wt-verify` | 常驻 | 配方自检（接入时）、agent 只读代码检索（后续 Issue 诊断） |
| `wt-build-<runId>` | 构建开始 → 终态后清理 | 流水线检出（替代现 runs/<runId> 的 clone） |
| `<用户本地目录>`（仅 LOCAL） | 用户自主，永不删除 | 用户开发 |

### 4.2 API

| 端点 | 说明 |
|---|---|
| `GET /api/v1/projects/{id}/worktrees` | 列出平台管理的 worktree（名称、HEAD、创建时间） |
| `POST /api/v1/projects/{id}/worktrees` | 手动建一个（{name, ref}）——为后续"agent 在隔离副本里试改"预留 |
| `DELETE /api/v1/projects/{id}/worktrees/{name}` | 删除（构建残留清理也走这里） |

### 4.3 并发与一致性

- 同一项目同时只允许一个活跃构建（TriggerScheduler 已保证项目级串行）→ worktree 不会互相踩
- worktree 名带 runId，天然唯一
- `git worktree prune` 定期清理失效登记（进程被杀留下的孤儿）

## 5. 接入流程（状态机，v2 修订）

```
INTAKE_FORM ─→ VALIDATING ─→ LINKING（收编/clone）─→ RECIPE_CHECK ─→ REGISTERED
     │             │                │                    │
     │             └→ 表单报错        └→ INTAKE_FAILED ──┘（重试 → LINKING）
                                              │
                              LOCAL: 校验用户目录 + git 收编（不动文件）
                              REMOTE: git clone --bare
```

**API（v2 修订）**：

| 端点 | 方法 | 说明 |
|---|---|---|
| `/api/v1/projects/intake/local` | POST | {projectId, localPath, type, gitInitIfMissing?} |
| `/api/v1/projects/intake/remote` | POST | {projectId, repoUrl, type, defaultBranch?, credentialRef?} |
| `/api/v1/projects/intake/{projectId}/status` | GET | 接入进度 |
| `/api/v1/projects` | GET / DELETE | 列表 / 下线（含"仅解除托管，不动本地目录"选项） |
| `/api/v1/projects/{id}/git/status` | GET | §3.2 本地/远端状态 |
| `/api/v1/projects/{id}/git/diff` | GET | §3.2 diff 摘要 |
| `/api/v1/projects/{id}/git/sync` | POST | fetch（LOCAL→bare / REMOTE→bare） |
| `/api/v1/projects/{id}/worktrees` | GET/POST/DELETE | §4.2 |

**配方自检**：在 `wt-verify` worktree 上跑（不再复制）：
1. 读 `ci/actions.yml` / Makefile / Taskfile → 6 个动作覆盖情况
2. `ci/pipeline.yml` 缺失 → 模板内容放进报告（不写回用户仓库）
3. 类型必备项检查（ruoyi-plus 要 Dockerfile 等）

## 6. 现有代码改造点（读码确认）

| 位置 | 现状 | v2 改造 |
|---|---|---|
| `BuiltInPipelineEngine.checkout()` | `git clone <workspace>/<id>/repo → runs/<runId>` | `git worktree add worktrees/wt-build-<runId> <sha>`；run 终态后 remove |
| `checkout()` 前置 fetch | `git fetch --all`（来源=repo 目录） | LOCAL：`git -C <用户目录> push agent HEAD` 或 `git fetch <用户目录路径>`；REMOTE：`git fetch origin`（bare 内） |
| `RecipeActionResolver.resolveCommit()` | 手读 `<root>/.git/HEAD` + ref 文件 | 改 `git rev-parse HEAD`（worktree/bare 都正确）；保留手读作回退 |
| `ActionService.workspace()` | `<workspace>/<projectId>` | 构建上下文改为 worktree 路径（由引擎传入，ActionService 不再自己拼） |
| `ProjectsProperties.ProjectDef` | 无来源字段 | 加 `source: LOCAL/REMOTE`、`localPath`、`repoUrl`、`linkedAt` |
| `ProcessExecutor` | 通用执行 | 不变（worktree 命令都是普通 argv） |
| `ProcessActionRunner`（Windows PATHEXT） | 已支持 git.exe 解析 | 不变 |
| 构建历史 | `_history/` 每项目一份 | 不变 |

**改造原则**：worktree 的创建/清理封装为 `GitWorktreeManager`（agent-infra 新类），
引擎与 intake 都调它，不散落 git 命令。

## 8. 风险与遗留问题（v2 更新）

| # | 问题 | 影响 | 对策 |
|---|---|---|---|
| R1 | **用户目录被 git init 时误伤** | 纯目录收编会创建 .git | 向导二次确认 + 明确告知；含 .git 的目录不受影响 |
| R2 | **用户目录的改动未 commit** | fetch 拿不到未提交内容 | status 报告显示未提交文件数；提示"构建只用已提交内容"（这是正确语义，不是缺陷） |
| R3 | **用户目录 .git 指向平台 bare 后误操作 push** | 用户可能 push 到 agent remote | remote 命名用 `agent` 并在向导说明；平台 bare 设置 `receive.denyNonFastForwards`，推送冲突即失败（不静默） |
| R4 | **Windows 路径空格/中文** | git 命令参数 | ProcessBuilder argv 数组传参天然安全（不经 shell）；文档记录 |
| R5 | **worktree 泄漏**（进程被杀没清理） | 磁盘/登记残留 | 定时 `git worktree prune` + 构建终态钩子清理 |
| R6 | **同一本地目录被两个项目收编** | 一个目录只能属于一个仓库（worktree 限制） | 收编前检查该目录 `.git` 是否已有 worktree 登记；冲突即报错 |
| R7 | **本地目录被用户删除** | fetch/worktree 失效 | status 探测 localPath 不存在 → 项目标记 DEGRADED，构建报可读错误 |
| R8 | **REMOTE 项目的"本地对比"** | clone 来的项目没有用户本地目录 | diff 只对 LOCAL 来源开放；REMOTE 只有 remote 分支间对比（PR 视角），status 里说明 |
| R9 | **项目存储仍是内存+yml** | 重启丢接入 | 不变（v1 P1 结论）：接入项落 SQLite |
| R10 | **runs/ → worktrees/ 命名迁移** | 历史构建目录残留 | 新构建写 worktrees/；旧 runs/ 保留只读，RunHistoryStore 不受影响 |

## 10. 前端设计（P2 · web 端）

### 10.1 设计原则（对齐现有 ChatView 的 DSH 视觉语言）

- **白底正文 + 白度差分层**：不做重卡片，层级靠 `--surface-sunken` / `--line-soft` 的微差
- **14px/1.85 正文、46-54rem 最大行宽**、mono 字体只用于 ID/sha/路径
- **状态即颜色**：`--ok` 绿 / `--warn` 黄 / `--danger` 红，配小圆点，不用大色块
- **Element Plus 只用轻组件**（input/tag/dialog/alert），列表和表单自己排——避免 EP 的"后台系统感"
- **异步任务一律轮询**：接入/clone 是长任务，表单提交后进入状态轮询视图，不转圈阻塞

### 10.2 信息架构与路由

```
路由（router.ts 新增）：
  /projects                    → ProjectListView（项目列表，新增）
  /projects/:id                → ProjectDetailView（项目详情：git 状态 + diff + worktree）
  /projects/intake             → ProjectIntakeView（接入向导，新增）

导航（AppAside.vue entries 新增）：
  { to: '/projects', icon: FolderOpened, label: '项目' }   ← 插在「对话」与「流水线」之间
```

页面关系：
```
项目列表 ──「接入项目」──→ 接入向导（表单 → 轮询 → 自检报告 → 完成）
   │
   └─ 点项目行 ──→ 项目详情
                    ├── 头部：项目名 / 来源标（LOCAL 路径 | REMOTE url）/ 状态标
                    ├── git 状态卡：分支、HEAD、本地改动数、领先/落后（origin 与 agent 双远端）
                    ├── diff 视图：提交列表 + 文件 ±stat（本地 vs 远端）
                    ├── worktree 列表：常驻/构建/用户目录，终态构建的可清理
                    └── 操作区：同步(fetch) / 构建验证(ci_run verify) / 下线(危险区)
```

### 10.5 轮询与错误形态（复用既有约定）

- 轮询：`setInterval` 2s + 组件卸载清理；连续 3 次失败降级为"暂停轮询 + 手动刷新按钮"
- 错误：`ApiError`（http.ts）直接 `ElMessage.error`；git 原始报错一律 mono 块展开展示（不吞）
- 空态：项目列表空时引导卡"还没有托管项目 → [接入第一个项目]"（直达向导）
- loading：局部 skeleton（列表）/ 步骤时间线（接入中），不用全屏遮罩
