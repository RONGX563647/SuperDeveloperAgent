## 0. 为什么改成方案 C

旧实现的三个问题（都在设计层，不在 UI）：

1. **部署语义在仓库脚本里**（`stack_deploy → node deploy.js ${tag}`）：平台不知道部署到哪、当前线上是哪个版本、能否回滚；
2. **L3 审批在流水线内被绕过**：`pipeline.yml` 与待构建代码同一 commit，"计划即审批"不成立；
3. **Agent 可自由部署但不可复用**：模型每次都"自由发挥"拼命令，既不可复现，也无法沉淀。

方案 C 的取舍：**流水线只做编排（检出 → 构建 → 测试 → 镜像 → 部署 → 健康检查），部署由平台部署器执行**。
仓库只声明"部署到哪"，不提供部署脚本。

## 1. 角色重定义

| 层 | 职责 | 不负责 |
|---|---|---|
| `ci/pipeline.yml` | 声明 stage 顺序 + `deploy:` 目标/端口 | 具体命令、部署动作 |
| `ci/actions.yml` | 每个动作的 argv（构建/测试/打镜像） | 部署、回滚 |
| 平台部署器（`Deployer` 端口） | 容器/进程/远端的实际发布、替换、回滚锚点 | 构建、测试 |
| 引擎（`BuiltInPipelineEngine`） | 编排、门禁、证据链、失败即停、on-failure 回滚 | 平台外的副作用 |

**Agent 边界不变**：模型只能 `ci_run`（白名单流水线）或 `run_action`（L2），不能新增命令，
更不能自由部署——部署只能通过 `deploy` 段 + 平台部署器。

## 2. pipeline.yml v3

```yaml
name: release

deploy:                    # 新增：部署声明（平台部署器据此执行）
  target: docker           # docker | host | server（运行时可被触发参数覆盖）
  port: 8080               # 对外端口（docker 映射 / host 监听）
  containerPort: 8080      # 容器内端口（仅 docker）
  healthPath: /healthz     # 健康检查路径（写进 endpoint 与健康门禁）
  artifact: backend/target/app.jar   # 可选：HOST 目标产物；空则自动找 target/*.jar

stages:
  - id: build
    type: action           # 动作 stage（命令来自 actions.yml / 内置默认）
    action: backend_build
    runner: container
  - id: test
    type: action
    action: backend_test
    runner: container
  - id: image
    type: action
    action: image_package
    runner: host
  - id: deploy
    type: deploy           # 新增：平台部署器执行
  - id: health
    type: health
    url: http://127.0.0.1:8080/healthz
    expected: 200

on-failure:
  - id: rollback
    type: rollback         # 新增：用上一版镜像重新部署（平台执行）
```

同一份文件既可被 `release` 使用，也可被 `verify` 使用；`verify` 自动剔除
`deploy` / `rollback` / `health` / `stack_deploy`（PR 检查语义不变）。

## 3. 三种部署目标

| 目标 | 实现 | 语义 | 回滚 |
|---|---|---|---|
| `docker` | `DockerDeployer` | `docker rm -f agent-deploy-<project>` → `docker run -d --restart unless-stopped -p host:container` | 用 `lastGood` 镜像重跑同一命令 |
| `host` | `HostDeployer` | 版本目录 `releases/<sha>/app.jar` + `java -jar --server.port=`，pid/日志落 `<workspace>/.agent/deploy/<project>/` | `current`/`previous` 指针轮转；rollback 启动 `previous` 版本，**启动失败不污染指针** |
| `server` | `ServerDeployer` | `docker save` → **JSch SFTP 上传** → 远端 `docker load` → `docker rm -f` → `docker run -d`（密码/密钥均支持；主机指纹 TOFU 记录） | 用 `previousImageRef` 重新部署（远端镜像不自动清理） |

**统一契约**（[Deployer.java](../platform/agent-domain/src/main/java/top/rongx/agent/domain/port/Deployer.java)）：

- `supports(target)`：注册表按目标选择实现；
- `deploy(request)`：不得抛异常，失败用 `DeployResult.failed(E-5xx, summary)`；
- 成功必须返回 `endpoint`（`http://127.0.0.1:<port><healthPath>`）与平台托管资源名（容器名 / pid 文件）；
- 重复执行必须幂等（先停旧、再起新）。

错误码（新增 E-5xx 段，接在 §4 总表之后）：

| 码 | 含义 |
|---|---|
| E-501 | 目标前置条件缺失（无镜像 / 无状态目录） |
| E-502 | 启动失败（容器起不来 / 进程退出 / 远端命令失败） |
| E-504 | HOST 目标缺少可运行 jar（前端静态产物请用 DOCKER） |
| E-505 | 目标未配置（SERVER 缺 host 或 key-path） |
| E-506 | pipeline.yml 缺少 deploy 段或目标非法 |
| E-507 | 无可用回滚版本（本项目尚无成功发布记录 / previous 指针） |
| E-508 | 流水线定义与默认分支不一致（部署配置未合并，见 §8） |

## 4. 部署器选型与"沉淀成工具脚本"

需求原话："agent 可以自由部署但不可复用，最好沉淀成工具脚本。"

落点：**把"部署"这个能力从 prompt 里收回到 Java 组件**。

- 以前：模型生成 `node deploy.js ${tag}` → 每个项目一份脚本、互不兼容、无法审计；
- 现在：模型/人只选择目标（docker/host/server）+ 端口，具体动作由 `DockerDeployer` / `HostDeployer` 统一执行；
- 复用方式：新增项目不需要写部署脚本，只需要 `deploy:` 段（由脚手架自动生成）；
- 可扩展：新增部署形态 = 新增一个 `Deployer` 实现 + 注册进 `Deployers`，不改流水线。

远程服务器配置（**推荐**：设置页「设置 → 服务器」维护，支持多台 + 测试连接 + 默认服务器；
`application.yml` 的 `agent.deploy.server.*` 仅作兜底，见 [设置说明](设置-服务器与模型连接-v1.md)）：

```yaml
agent:
  deploy:
    server:
      host: 10.0.0.12          # 必填；为空时 SERVER 目标 E-505
      port: 22
      user: deploy
      key-path: ~/.ssh/id_ed25519   # 必填（BatchMode=yes，免密）
      remote-dir: /opt/agent/deploy
```

> 远端机器需具备：docker、可被 `ssh` 免密登录、`remote-dir` 可写。
> 平台不会自动清理远端镜像（避免 prune 掉回滚锚点）。

## 5. 脚手架：导入项目即生成脚本

`RecipeScaffolder`（[实现](../platform/agent-infra/src/main/java/top/rongx/agent/infra/scaffold/RecipeScaffolder.java)）
只读扫描仓库，按结构生成 `ci/pipeline.yml` + `ci/actions.yml`：

| 探测 | 生成 |
|---|---|
| 根 `pom.xml` / `build.gradle` | `backend_build`（mvn package / gradle build）+ `backend_test` |
| 根 `package.json` | `frontend_build`（按 `pnpm-lock.yaml` / `yarn.lock` / `package-lock.json` 选包管理器） |
| `backend/` + `frontend/` | monorepo：每个 stage 带 `workdir` |
| 根 `Dockerfile` | `image_package`（`docker build -t ${tag} .`） |
| 以上都没有 | 生成骨架 + 告警 `UNKNOWN` |

生成规则：

- 部署 stage + 健康检查 + `on-failure: rollback` 默认写入（按所选目标）；
- `host` 目标额外告警"仅 Java jar"；`server` 目标告警"未实现，占位"；
- **默认不覆盖已有文件**（`overwrite=false`），避免吞掉人工调过的 YAML；
- 写入仓库工作树，不自动 commit——**改动随代码 review**。

API：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/projects/{id}/scaffold?target=docker` | 预览：返回 `{stack, files[{path,content}], notes}`，不写盘 |
| POST | `/api/v1/projects/{id}/scaffold?target=docker&overwrite=false` | 落盘：返回 `{written, skipped, notes}` |
| GET | `/api/v1/ci/deploy/targets` | 部署目标列表 + 可用性（server 未配置时 available=false） |

> MANAGED（bare 仓库）没有工作树，接口会明确拒绝并提示改用本地目录接入。

## 6. 触发时选择部署目标

`POST /api/v1/ci/pipelines/{id}/run`

```json
{ "projectId": "RY", "gitSha": "abc1234", "deployTarget": "host" }
```

- `deployTarget` 为空 → 用 `pipeline.yml` 的 `deploy.target`；
- 覆盖值随运行记录（`RunState.deployTargetOverride`），`deploy`/`rollback` stage 共用；
- 页面：触发条新增"部署目标"下拉（不可用项置灰并给出原因），运行条展示本次实际目标。

## 8. 审批补强（已实现：E-508）

规则：**只要 pipeline.yml 声明了 `deploy` 段，本次运行的 `ci/pipeline.yml` blob 必须与
默认分支（bare HEAD / main / master）上的同一文件完全一致**，否则拒绝执行（E-508）。

- 为什么用 blob 哈希而不是解析 deploy 段比对：日志管道会截断尾部，解析可能得到 null，
  从而"看起来一致"——比不校验更危险；哈希对比是确定性的。
- 哪些改动会被拦：**任何**未合并的 pipeline.yml 改动（不仅 deploy 段）。语义是
  "流水线定义属于默认分支"，与 Jenkinsfile-from-SCM 一致。
- 无法读取默认分支时（新仓库还没有 main/master）**放行并写日志**，便于早期接入；
  日志里会留 `[guard]` 行，可审计。

> 后续可加：prod 环境额外要求 `confirmToken`（把"默认分支已审"升级为"本次发布已审"）。
