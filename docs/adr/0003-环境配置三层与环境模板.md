# ADR-0003：环境配置三层——环境模板 + 项目差异 + `secret://`

- **状态**：通过
- **日期**：2026-11-08
- **关联**：[环境模板 v2](../环境变量与环境模板设计-v2.md)、[配置事实层方案](../环境配置事实层与分环境门控-方案-v1.md)

## 背景与痛点

环境变量原先散落在项目 `.env`、部署脚本和 Agent 对话里：同一变量多处定义、密钥明文、Agent 可能把猜测值写进环境。

## 问题陈述

变量配在哪、以谁为准、Agent 是否有权写入？

## 候选方案

| 方案 | 收益 | 风险 |
|---|---|---|
| A. 全部由项目 `.env` 决定 | 简单 | 跨项目重复、密钥明文、环境间覆盖关系不清 |
| B. 平台集中维护全部变量 | 一致性好 | 项目差异被抹平；平台成为瓶颈 |
| C. 三层：环境模板 → 项目覆盖 → 部署时合并 | 变量配一次、项目只写差异、部署只注入合并结果 | 需要解析优先级与冲突提示 |

## 决策

选 **C**，并叠加两条硬约束：

1. **密钥只以引用形式存在**：`secret://<key>` 由密钥库解密后注入，任何接口/工具不回显明文（`****`）；
2. **Agent 只能建议映射，不能擅自使用**：`env_mapping_draft` 产出 DRAFT 绑定，`deploy_run` 必须携带人工确认过的 `binding_id`（E-703）；解析冲突或缺失时返回 `NEED_USER_INPUT` 并要求停止执行。

## 影响范围

- 代码：`ConfigResolver`（解析优先级唯一实现）、`EnvProvisioner`（中间件按需创建）、`EnvBindingPort`；
- 文档：`docs/环境变量与环境模板设计-v2.md` 为决策正文；
- 安全：`env_summary`/`env_var_probe` 只回数量、归属与健康，不回值。

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| 解析优先级被后人改坏 | 解析器单一实现，工具与 HTTP 共用；回归测试覆盖 resolved/missing/conflicts |
| 中间件按需创建导致资源膨胀 | 仅 dev/test；prod 需人工确认；容器归属写入覆盖变量可追溯 |

## 后果

环境配置从「散落文本」变成「可解析、可审计、可分环境门控」的事实层；代价是新增项目要维护少量覆盖项。
