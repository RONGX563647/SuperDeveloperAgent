# ADR-0001：独立平台，而非改造若依

- **状态**：通过
- **日期**：2026-11-02
- **关联**：[v3 独立平台可行性](../devops-agent-独立平台-可行性分析-v3.md)、[v2 Vue-Plus 重评](../ruoyi-vue-plus-agent-可行性分析-v2.md)、[v1 若依基线](../ruoyi-agent-可行性分析与市场调研.md)

## 背景与痛点

团队需要一个「能读代码仓库、能跑流水线、能部署、能自我诊断」的研发运维 Agent。最初的路径是在若依（RuoYi）上加 AI 能力，但若依 4.8.3 是 Java 8 + Shiro + Thymeleaf，代码生成器以「写盘为准」，与 Agent 需要的「只读 + 提案 + 人工确认」模型冲突。

## 问题陈述

在若依上改造，还是新建一个独立平台？

## 候选方案

| 方案 | 收益 | 风险 / 成本 | 适配度 |
|---|---|---|---|
| A. 改造若依 4.8.3 | 现成权限/菜单/代码生成 | Java 8、Shiro、生成器写盘；升级到 JDK21 需重写安全层 | 低 |
| B. 基于 RuoYi-Vue-Plus 6.1 | Sa-Token、JDK21、自带 Spring AI + MCP | 与若依生态版本耦合；AI 仍要按我们的工具面重写；多项目/环境隔离需大改 | 中 |
| C. 独立平台，借若依的工程经验 | 模块边界自定；domain 零框架便于 ArchUnit；工具面从零按最小权限设计 | 页面、权限、部署都要自己写 | 高 |

## 决策

选 **C**。平台按 8 个 Maven 模块分层（domain / governance / infra / executor / tools / runtime / gateway / spec-checks），前端 Vue3 + Element Plus 独立仓库目录；只借鉴若依的「角色权限 + 菜单」思路，不复用其代码。

## 影响范围

- 代码：全仓结构；domain 不依赖 Spring，executor 不依赖 LLM；
- 文档：本 ADR 取代 v1/v2 两条改造路线（文档保留作证据，状态为「历史」）；
- 运维：平台自身成为被运维对象，需要自己的部署/回滚手册（见 [运维手册](../operation/README.md)）。

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| 重复造轮子（权限、审计、密钥） | 只造与 Agent 安全边界相关的部分；其余用成熟库（Sa-Token、AES-GCM、SQLite） |
| 页面工作量被低估 | 页面收敛为 7 个：登录 / 助手 / 工作区 / 流水线 / 项目 / 接入 / 设置 |

## 后果

平台可独立演进，工具面与安全边界可被 ArchUnit 与规约测试守住；代价是所有「框架便利」都要自己补。
