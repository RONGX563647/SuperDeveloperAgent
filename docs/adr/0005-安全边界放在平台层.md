# ADR-0005：安全边界放在平台层，工具不可自我批准

- **状态**：通过
- **日期**：2026-11-12
- **关联**：[项目规约 §4.10](../项目规约-v1.0.md)、[Code Wiki §5.3/§5.16](../Code-Wiki.md)

## 背景与痛点

Agent 的 ReAct 循环在「需要人工确认」模式下容易卡死或反复询问；若把确认权交给模型（例如让模型调用 `confirm` 完成确认），等于让模型自己给自己授权。

## 问题陈述

确认令牌由谁签发？破坏性操作如何既可用又不可被模型滥用？

## 候选方案

| 方案 | 收益 | 风险 |
|---|---|---|
| A. 模型在对话里确认即可 | 体验顺畅 | 模型可自我授权；审计无锚点 |
| B. 平台层确认：令牌只能由已登录用户经 HTTP 签发 | 责任可追溯；与 UI 一致 | 多一步人工操作 |
| C. 全程禁用写操作 | 绝对安全 | 产品失去价值 |

## 决策

选 **B**，并明确三条边界：

1. `confirm` **工具存在但不签发令牌**——它只把变更单推给当前操作人（返回 `PENDING_USER_CONFIRMATION`），令牌只由已登录用户的 `POST /changes/{id}/confirm` 签发，一次性、与 `specHash` 绑定；
2. **破坏性动作识别在平台层**：`DangerousActionPolicy` 按动作名/配方关键词（`rm -rf`、`drop table`、`git reset --hard`、`migrate`、`rollback` 等）判定 L2，即使 dev/test 关闭模型侧确认（BYPASS），平台仍会要求人工确认；
3. **频次兜底**：同一操作人 + 项目 + 动作 10 分钟内最多 3 次，超限 `E-709`。

## 影响范围

- 代码：`AgentScopeApprovalGateway`、`ChangeRegistry`、`ConfirmTokenService`、`DangerousActionPolicy`、`ActionService`；
- 文档：规约 §4.10 与 Code Wiki §5.3/§5.16 同步；
- 体验：前端审批卡片与「变更」页复用同一套令牌流程。

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| 关键词识别漏判（语义级破坏） | 明确写入边界：生产动作仍受环境门控 + 令牌约束；不承诺语义审计 |
| 确认步骤降低可用性 | 只对 L2/L3 生效；L0/L1 不打扰；提供一次确认批量执行 |
| 令牌泄漏 | 一次性 + 过期时间 + `specHash` 不匹配即失效 |

## 后果

安全责任锚定在「已登录的人」，而不是模型的自觉；后续接 MCP 写工具时沿用同一套门禁即可。
