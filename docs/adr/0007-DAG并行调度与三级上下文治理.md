# ADR-0007：调度 Agent 改 DAG 并行 + 三级上下文治理

- **状态**：通过
- **日期**：2026-11-15
- **关联**：[Code Wiki §5.18](../Code-Wiki.md)、`WorkspaceDispatchScheduler`、`ToolResultCache`、`ConversationContextTrimmer`

## 背景与痛点

工作区调度 Agent 原先只有 `conversation_send` + `conversation_wait`：派发 N 个子目标时，模型必须
「send → wait 到终态 → 再 send 下一个」串行推进。一次 `wait` 最多 60 秒，三个互不依赖的目标就会
把一轮对话拖到 3 分钟以上；而且模型容易在「等」上反复轮询。与此同时，长会话里工具输出无上限、
历史全量回放，token 成本随轮次线性增长；重复的只读查询也每次都真实打仓库/运行时。

## 问题陈述

如何在不改变「平台层安全边界」的前提下，让多个子任务并行推进、尽早结束，并让每轮上下文成本可控？

## 候选方案

| 方案 | 收益 | 风险 / 成本 |
|---|---|---|
| A. 继续串行 wait，靠提示词鼓励少派发 | 零改动 | 物理上无法并行；长任务必然阻塞 |
| B. 调度器内部用线程池替模型轮询 | 模型简单 | 仍是串行等待；无法表达依赖关系 |
| C. 新增 DAG 工具：一次派发、并行等待、失败熔断 | 并行度由计划表达；依赖/提前终止显式化；模型只调用一次 | 需要领域模型、超时/取消与循环依赖校验 |
| D. 引入外部工作流引擎（如 Temporal） | 强持久化 | 部署形态变重，与当前 SQLite 单机模型不匹配 |

上下文侧：

| 方案 | 收益 | 风险 / 成本 |
|---|---|---|
| 只加历史截断 | 简单 | 单条巨型工具输出仍会撑爆一轮 |
| 只加工具输出截断 | 简单 | 历史轮次仍无限增长 |
| 工具输出预算 + 语义缓存 + 落盘裁剪 | 三层互补，成本可解释 | 需要失效策略，缓存不能返回过期状态 |

## 决策

选 **C + 三层上下文治理**：

1. **DAG 并行调度**（`WorkspaceDispatchScheduler`）：
   - 工具 `workspace_dispatch` 接收节点数组（`id/message/depends_on/required/timeout_seconds`），
     无依赖节点在 `max_parallel` 内同时派发；每个节点在自己的虚拟线程上等待，
     主循环只等「任意一个完成」，因此总耗时接近最慢节点而非逐个累加；
   - 依赖全部成功的节点才会派发；依赖失败则整条链路 `SKIPPED`，不占用运行配额；
   - **提前终止**：`required` 节点失败且 `abort_on_failure=true` 时停止派发剩余节点；
     `required` 节点全部成功后，未开始的可选节点不再派发，在跑的可选节点直接 cancel；
   - 派发前用 Kahn 拓扑排序拒绝循环依赖；单节点超时会 cancel 对应 run；
   - **全局超时**：整张 DAG 还有总时长上限（`max_duration_seconds`，默认 600 秒），到点取消在跑节点、
     未开始节点标记 `SKIPPED`，并带上 `early_stopped` 原因返回已完成的部分结果。
2. **前缀缓存**：`GenerateOptions.cacheControl(true)`（`agent.model.prefix-cache`，默认开）。
   系统提示与工具 schema 每轮保持稳定（工具装配顺序固定、提示词不含时间戳等易变内容），
   由模型服务端复用前缀 KV；不支持该字段的兼容服务会忽略，无副作用。
3. **语义缓存**（`ToolResultCache`）：只读工具结果按 `project|env|worktree|user + 工具 + 归一化参数`
   缓存，参数词元 Jaccard ≥ 0.9 视为同一问题；TTL 90 秒 + LRU 512 条；任何写工具成功执行后
   清空同 scope 缓存，避免「刚改完读到旧值」。无需向量库与外部依赖。
4. **上下文精益**：
   - 工具输出预算：`CachingAgentTool` 统一截断超过 `agent.tools.max-output-chars`（默认 12000）的文本；
   - 历史预算：`ConversationContextTrimmer` 在状态落盘前裁剪最早消息（默认 60000 字符 / 至少 24 条），
     永远保留开头 SYSTEM 提示，且窗口不以 TOOL 消息开头（否则会留下无主的工具结果）；
   - 提示词要求：拿到足够信息立即回答，不复述长日志。
5. **边界与可观测**：
   - 服务端用 `agent.workspace.dispatch.max-parallel` / `max-duration-seconds` 收紧模型传入的计划
     （只能变小不能放大），避免一次派发吃满工作区运行配额；
   - 调度入口 SSE 默认 10 分钟（`agent.chat.super-timeout-ms`），普通对话默认 3 分钟
     （`agent.chat.timeout-ms`）；`SseHeartbeat` 每 15 秒发注释行保活，与业务事件共用发送锁；
   - 语义缓存命中率通过 `workspace_snapshot` 末尾的 `tool_cache: hits/misses/hitRate/...` 暴露。

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| 语义缓存返回过期结果 | 默认只缓存只读工具；TTL 90 秒；写工具成功即清 scope；scope 含 env/worktree，跨环境影响隔离 |
| 相似度误判 | 阈值 0.9，且只在同 scope + 同工具内比较；宁可 miss 不返回错结果 |
| 并行放大下游压力 | `max_parallel` 上限 8，默认 4；服务端配置可进一步收紧；沿用现有运行配额与限流 |
| 提前终止误杀有用工作 | 只取消 `required=false` 的节点；必需节点始终跑完 |
| 全局超时丢结果 | 返回已完成节点；`early_stopped` 载明「总时长超过 Ns」，模型可改用 `conversation_status` 续查 |
| 长任务 SSE 被代理/超时截断 | 调度入口默认 10 分钟；15 秒心跳保活；超时/断开统一取消上游并释放配额 |
| 上下文裁剪破坏工具调用配对 | 只从 USER 轮次边界切入，且不动开头 SYSTEM 消息 |

## 后果

互不依赖的子任务从「逐个 60 秒等待」变为并行推进；一轮对话在拿到必需结果后可以立即结束。
代价是引入计划/依赖的认知负担（由工具 schema 与提示词示例约束）、以及缓存失效逻辑；
两者都有单测覆盖（`WorkspaceDispatchSchedulerTest`、`ToolResultCacheTest`、`ConversationContextTrimmerTest`）。
