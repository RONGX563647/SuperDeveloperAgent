# 流水线工作台 · 使用指南 v1

> 面向：要在本平台接入项目并跑 CI/CD 的开发者
> 读完后你能：接入一个项目 → 写两个 YAML → 从页面触发/重跑/回滚 → 看懂每条失败信息

---

## 0. 30 秒概览

这套流水线的核心思想是**方案 D**：

- **流水线和命令都是仓库里的 YAML 数据**（人写、review 过、随代码版本化）；
- **平台不执行任何"代码"**，只做四件事：检出指定提交 → 按你声明的 stage 顺序跑 → 失败即停 → 留下证据（每步结果/产物 sha256/镜像 digest/日志）；
- **AI 只能"选择"动作，不能"编写"命令**——这是安全边界，不是功能限制。

一次发布的完整链路：

```
git 提交 → 页面触发（或 Gitee push 自动触发）
  → checkout 指定 sha → build → test → image → deploy → health
                                ↘ 任一步失败：停止 + 自动执行 on-failure（回滚）
```

## 1. 接入一个项目（一次性，约 5 分钟）

### 1.1 放置源码仓库

引擎按 **`<工作区>/<projectId>/repo`** 找源码（`application.yml` 的 `agent.workspace.root`，默认 `./data/workspaces`）：

```
platform/data/workspaces/
└── RY/                      ← projectId（页面上的项目名）
    ├── repo/                ← 你的 git 仓库（引擎从这里 clone）
    └── runs/                ← 每次运行一个独立目录（平台自动创建）
```

```bash
mkdir -p platform/data/workspaces/RY
git clone https://gitee.com/<你>/<项目>.git platform/data/workspaces/RY/repo
```

> 也可以是本地路径的裸克隆，引擎用 `git clone --no-checkout` + `checkout --detach <sha>`，所以 repo 只要有 `.git` 即可。

### 1.2 在仓库里写 `ci/pipeline.yml`（流水线声明）

```yaml
name: release                    # 流水线名（页面下拉里显示的就是它）

deploy:                          # 平台部署器声明（方案 C：部署不再写仓库脚本）
  target: docker                 # docker | host | server（页面触发时可覆盖）
  port: 8080
  containerPort: 8080
  healthPath: /healthz

stages:
  - id: backend                  # stage 标识（历史/时间线里显示）
    type: action
    action: backend_build        # 必须是动作白名单里的名字（见 §2）
    runner: container            # container=容器沙箱 | host=宿主机
    workdir: backend             # 可选：monorepo 子目录
    image: maven:3.9-eclipse-temurin-21   # 可选：该 stage 专用工具链镜像
  - id: frontend
    type: action
    action: frontend_build
    runner: container
    workdir: frontend
    image: node:20-alpine
  - id: image
    type: action
    action: image_package        # docker build 必须在 host（沙箱内无 docker socket）
    runner: host
  - id: deploy
    type: deploy                 # 平台部署器执行（docker / host / server）
  - id: health                   # 发布门禁：真实 HTTP 探测
    type: health
    url: http://127.0.0.1:8080/healthz
    expected: 200

on-failure:                      # 任一 stage 失败后按序执行（自动回滚就写这里）
  - id: rollback
    type: rollback               # 用上一个成功版本重新部署（平台执行）
```

> 不想手写？项目页「生成流水线脚本」会扫描仓库结构，自动产出上面两份文件（见 [发布编排与平台部署器-v1](发布编排与平台部署器-v1.md) §5）。

### 1.3 在仓库里写 `ci/actions.yml`（每个动作的命令）

```yaml
actions:
  backend_build:                       # 白名单动作：在配方里给它们具体命令
    run:
      - ["mvn", "-B", "-q", "-DskipTests", "package"]
    produce: ["target/*.jar"]          # 声明产物：构建完没找到 → 直接判失败（E-401）
    timeout: 5m

  backend_test:
    run: [["mvn", "-B", "test"]]
    timeout: 5m

  frontend_build:
    run:
      - ["npm", "install", "--no-audit", "--no-fund"]
      - ["npm", "run", "build"]
    produce: ["dist/index.html"]
    timeout: 5m

  image_package:
    run: ["docker", "build", "-q", "-t", "${tag}", "."]

  stack_deploy:
    run: ["node", "deploy.js", "${tag}"]     # 部署逻辑写在仓库脚本里，review 过

  stack_rollback:
    run: ["node", "deploy.js", "${tag}"]     # 回滚时 ${tag} 由平台替换为上一个成功版本
```

**规则**：

| 规则 | 说明 |
|---|---|
| `run` 是 argv 数组 | 平台用 `ProcessBuilder(List)` 直执行，**不经 shell**——所以不能写 `&&`、`\|`、`\|\| true` |
| 多条命令 = 多个 argv 数组 | 按序执行，任一条失败整个动作失败 |
| `${tag}` `${gitSha}` `${gitSha7}` | 平台注入的变量；`tag = ci-e2e:<sha7>`，回滚时自动换成上一个成功 tag |
| `produce` 是 glob | 相对 `workdir`；声明了但没生成 → E-401（防配方过期静默成功） |
| 命令来自仓库 | **改配方 = 改代码**，走 review；模型/AI 无权新增命令 |

## 2. 动作白名单（6 个，不能自造）

| 动作 | 级别 | 默认命令（仓库无覆盖时） |
|---|---|---|
| `backend_build` | L2 可直接执行 | `mvn -B -q -DskipTests package` |
| `backend_test` | L2 | 无默认（必须写配方） |
| `frontend_build` | L2 | `pnpm install --frozen-lockfile --ignore-scripts` + `pnpm build` |
| `image_package` | L2 | 无默认（必须写配方，需要 host） |
| `stack_deploy` | **L3 需人工确认** | 无默认 |
| `stack_rollback` | **L3 需人工确认** | 无默认 |

- L2：流水线里直接跑（仅限 test/dev 环境）；
- L3：单独触发时走「登记变更 → 人确认 → 带令牌执行」；**流水线内的 L3 由 pipeline.yml 本身充当已批准的计划**。

## 3. 日常使用（页面操作）

### 3.1 触发一次运行

> **前提：`ci/pipeline.yml` 必须已提交到你要构建的那个分支。**
> 构建检出的是**提交**（`git worktree add <sha>`），不读工作区里未提交的改动——
> 所以"生成了脚本但忘了 commit"会明确报 `E-220`，而不是给你一个看不懂的路径错误。

打开 `流水线工作台`：

1. **流水线下拉**选 `release`（名字来自 pipeline.yml 的 `name`；另有内置 `verify` = 只跑构建，不部署）；
   - 下拉为空并提示"该仓库还没有 ci/pipeline.yml"时：去「项目」页点「生成流水线脚本」→ 提交 → 回来刷新；
2. **sha 框**：打开页面时已自动预填最近一次构建的提交，改成本次要构建的 7-40 位 sha；
   - 框旁有「上次成功：xxxxxxx」，点一下即填入最近成功版本；
3. 点 **运行**。

右侧运行详情实时刷新（1s 轮询）：stage 时间线 → 产物（sha256）→ 日志（可跟随/复制）。运行中 Header 有「取消」按钮。

### 3.2 从历史重跑

构建历史每条 hover 会出现 **重跑按钮**：用该提交重跑同一条流水线（相当于"回滚到某个版本"的最常用方式——重新部署旧镜像由 deploy 配方负责）。

### 3.3 自动触发（Gitee push）

在 Gitee 仓库 → 管理 → WebHooks → 添加：

- URL：`http://<平台地址>:8090/api/v1/webhooks/gitee/push`
- 密码：与平台配置 `AGENT_WEBHOOK_GITEE_SECRET` 一致（未配置时平台**拒绝所有 webhook**，fail-closed）
- 事件：Push

每次 push 后平台取 `after`（新提交 sha）自动触发 `verify` 流水线（构建+测试，不部署）；同一 commit 重复推送只触发一次（幂等）。

## 4. 失败信息怎么看

| 现象 | 错误码 | 含义 / 怎么处理 |
|---|---|---|
| 点「运行」弹出提示，没有产生新 run | **E-220** | 该提交里没有 `ci/pipeline.yml`。两种成因分开提示：仓库压根没有 → 去「项目」页「生成流水线脚本」；工作区有但没提交 → `git add ci && git commit` 后重跑（构建只读提交内容） |
| stage `pipeline-def` 变红 | **E-221** | `ci/pipeline.yml` 有语法/结构错误 → 按摘要里的 YAML 报错改；stage 只能引用白名单动作 |
| stage 变红，`errorCode=E-101` | E-101 | **你的代码/测试失败**——看该 stage 日志尾部定位 |
| `E-201` | E-201 | 动作没有配方或命令为空 → 检查 `ci/actions.yml` 是否覆盖该动作 |
| `E-202` | E-202 | 配方把 shell（sh/bash/cmd）当命令 → 平台拒绝，改成 argv 形式 |
| `E-209` | E-209 | 命令不存在（如容器镜像里没有 mvn）→ 换带工具链的 `image:` |
| `E-302` | E-302 | 超时 → 加大配方 `timeout`，或优化构建 |
| `E-401` | E-401 | 声明的产物没生成 → 代码改了配方没跟上，更新 `produce` |
| `on-failure:xxx` 出现在时间线 | — | 失败后自动执行的补救动作（通常是回滚），它的结果也要看 |

> 历史落盘在 `<工作区>/_history/<runId>.yml`，重启平台后历史仍在，可从页面点开旧 run。

## 5. 沙箱与安全（跑真实构建前必读）

| 项 | 默认 | 说明 |
|---|---|---|
| `agent.sandbox.mode` | `auto` | Docker 可用 → 容器执行；不可用 → 回退宿主（会打 WARN）。`docker` 强制容器，无 Docker **启动失败** |
| 容器约束 | — | 非 root(uid 1000) / `--cap-drop ALL` / `no-new-privileges` / 内存·CPU·pids 限额 |
| `agent.sandbox.network` | `bridge` | 默认可拉依赖；生产建议 `build-net` + 防火墙限制内网；`none` 仅发布期（需缓存预热） |
| 依赖缓存 | `/cache/m2`、`/cache/npm` | 平台自动挂命名卷并初始化属主；同一项目重复构建显著加速 |
| 凭据 | **不注入** | 容器里没有任何密钥；无私服时无需配置 |

## 7. 已知边界（不是 bug）

1. `docker build` / 部署类 stage 必须 `runner: host`（沙箱内无 docker socket，这是**故意的**——挂 socket 等于给容器宿主机权限）；
2. 无并发队列面板：同项目运行自动 FIFO 串行，第二个 run 会排队（状态 PENDING），但没有"排队中"的可视化；
3. 会话/构建历史是文件存储（`_history/*.yml`），单机够用，换 MySQL 需替换 `RunHistoryStore` 一个类；
4. 取消作用于 stage 边界与进程终止（kill），已进入的 `docker run` 容器由 `--rm` 随进程回收；
5. 不做 step 级续跑（Jenkins durability）：失败只能整条重跑——5 分钟内的流水线，重跑比恢复更快更可信。
