# 项目接入设计：引入项目到平台（v1）

> 日期：2026-11-08 ｜ 前置：[多项目托管设计 v4](多项目托管设计-v4.md)、[流水线执行器规约 v1.0](规约-流水线执行器-v1.0.md)
> 目标：回答「项目从哪来（Gitee clone / 本地选取）、放哪、怎么接入」，并识别剩余问题。

---

## 0. 一句话结论

**双来源接入（Gitee clone 为主、本地导入为辅），统一落在 `AGENT_WORKSPACE_ROOT/<projectId>/repo`；
接入 = 登记项目 + clone/导入 + 配方自检，目标「半天接一个项目」。**

---

## 1. 现状盘点（读码确认）

| 事实 | 位置 | 对接入设计的影响 |
|---|---|---|
| 项目清单已是配置驱动（`agent.projects`） | `application.yml:31-49` | 接入即"加一段配置"，无代码改动 |
| 工作区布局约定 `<workspaceRoot>/<projectId>/repo` | `BuiltInPipelineEngine`（clone 来源）、`ActionService.workspace()` | **接入必须产出这个布局**，否则流水线/动作全断 |
| 引擎只从**本地已有** `repo/` clone 到 `runs/<runId>` | `BuiltInPipelineEngine.checkout()` | ⚠️ **没有"首次接入 clone"动作**——这是当前最大缺口 |
| fetch 是尽力而为（失败继续） | `BuiltInPipelineEngine.checkout()` | 离线/无远端场景可工作 |
| `ci/actions.yml` / Makefile / Taskfile 解析已完备 | `RecipeActionResolver` | 接入后必须自检"有没有配方"，否则 run_action 必失败 |
| `agent.sandbox.mode=process` 时 Windows 用 PATHEXT 解析 | `ProcessActionRunner` | 本地导入 + Windows 宿主构建可行 |
| webhook 按托管仓库名反查 projectId | `GiteeWebhookController` | clone 完成前 webhook 触发会 400，属预期 |

## 2. 项目从哪来：双来源

### 2.1 来源 A：Gitee/GitLab clone（主路径）

```
接入向导（三步）：
1. 填仓库 URL（https）+ 可选 token（私有库）
2. 选项目类型（ruoyi-plus / generic-java / static）→ 决定能力集与工具装配
3. 平台执行：clone → 配方自检 → 登记
```

**clone 策略**：
```bash
git clone --no-checkout <url> <workspaceRoot>/<projectId>/repo   # 省磁盘
git -C .../repo checkout --detach <defaultBranch的HEAD>          # 落一个确定提交
```
- `--no-checkout`：工作区只留 `.git`，构建时按 sha 检出到 `runs/`，磁盘省一半
- 私有库 token：**只用于 clone/fetch 命令，不落盘**——放在 `ProjectCredential` 引用
  （v4 §2.2 的 `(project, env, capability=repo_read)` 切片）；`.env` 只放平台自身的模型 key
- 首次 clone 失败（网络/权限）：登记为 `status=INTAKE_FAILED`，向导界面显示 git 原始报错，可重试

### 2.2 来源 B：本地项目选取（辅助路径，开发/演示场景）

```
接入向导（三步）：
1. 填本地路径（如 E:\CODE\shop-mall）—— 平台校验：目录存在 + 含 .git 或可初始化
2. 选项目类型
3. 平台执行：复制（非移动！）到工作区 → 自检 → 登记
```

**为什么复制而不是引用原路径**：
- 平台构建会 `git fetch`/`checkout`，绝不能动用户自己的工作副本
- 沙箱非 root（1000:1000）跑构建，用户目录权限不可控
- Windows 长路径/中文路径 + Docker 卷挂载是已知坑，复制到规范工作区一次解决

**本地导入的变体**：无 `.git` 的纯目录 → `git init + 首次提交`（标记 `repoType=local`），
流水线 checkout 逻辑不变；或 `git init + git remote add origin <url>`（可选后续推远端）。

### 来源决策表

| 场景 | 用哪个 | 原因 |
|---|---|---|
| 平台自身仓库 | 本地导入 | 平台构建自己 = 递归，clone 自己无意义 |
| 首个真实业务项目 | Gitee clone | webhook/构建/发布全链路都要走 |
| 本地随手测一个开源项目 | 本地导入 | 不想 fork/push 到自己账号 |
| 私有库无 token | 本地导入（临时） | 先跑通，再补 token 转 clone 源 |

## 3. 项目放哪：工作区布局（唯一布局）

```
${AGENT_WORKSPACE_ROOT}/            # 默认 ./data/workspaces（.gitignore 已含 data/）
├── RY/                             # <projectId>
│   ├── repo/                       # git 仓库（--no-checkout，只留 .git）
│   │   └── .git/
│   ├── runs/<runId>/               # 每次流水线的检出与构建（引擎已实现）
│   └── _history/                   # 构建历史 YAML（RunHistoryStore 已实现）
├── SHOP/
│   └── ...
```

**规则**：
1. **一个项目一个目录**，目录名 = projectId（`[A-Z][A-Z0-9_]{1,15}`，校验防路径穿越）
2. `repo/` 是 clone 目标；`runs/` 是引擎的检出/构建产物；`_history/` 是构建历史——三者引擎已按此布局读写，接入不要发明新布局
3. `data/` 已在 `.gitignore` → 工作区不入库
4. 磁盘预算：每项目 repo 元数据 ~50-200M + 每次运行检出 ~200-500M；
   保留最近 N=20 次 run（**新增清理任务，见 §6-P3**），8 项目 × 20 run × 400M ≈ 64G 上限——单机 1T 盘无压力
5. 服务器部署时 `AGENT_WORKSPACE_ROOT=/opt/agent-workspaces`（独立盘/分区优先）；
   开发机默认 `./data/workspaces`

### 本地导入的路径校验（防穿越）

- projectId 白名单正则 `[A-Z][A-Z0-9_]{1,15}`，仓库根由平台拼装，**用户永远不提供路径片段**
- 本地导入的"源路径"仅读取复制，不作为运行时路径

## 4. 接入流程（状态机）

```
INTAKE_FORM → CLONING → RECIPE_CHECK → REGISTERED
     │            │            │
     │            └→ INTAKE_FAILED（git 报错原样展示，可重试）
     │                         └→ 重试 → CLONING
     └→ 校验失败（URL/projectId 重复/类型未知）→ 表单报错
```

**API（新增 ProjectIntakeController）**：

| 端点 | 方法 | 说明 |
|---|---|---|
| `/api/v1/projects/intake/clone` | POST | {projectId, repoUrl, type, defaultBranch?, credentialRef?} |
| `/api/v1/projects/intake/local` | POST | {projectId, sourcePath, type}（校验后复制） |
| `/api/v1/projects/intake/{projectId}/status` | GET | 查接入进度（CLONING/RECIPE_CHECK/REGISTERED/INTAKE_FAILED） |
| `/api/v1/projects` | GET | 项目列表（现用 InMemory + yml，接入后转 DB 见 §6-P1） |
| `/api/v1/projects/{id}` | DELETE | 下线项目（停 webhook 触发，工作区保留可选清理） |

**配方自检（RECIPE_CHECK，决定"半天接入"能否达成）**：
1. 读 `<workspace>/<id>/repo/ci/actions.yml` 或 Makefile/Taskfile → 列出 6 个动作的覆盖情况
2. 检查 `ci/pipeline.yml`：无则生成**模板**（backend_build→backend_test→image_package→health）供用户改
3. 检查项目类型必备项：`ruoyi-plus` 需要 Dockerfile；`static` 需要 build 产物目录声明
4. 输出自检报告（JSON + 文本）：
   ```json
   {"ready": true, "actions": {"backend_build": "ci/actions.yml#backend_build", ...},
    "pipeline": "ci/pipeline.yml", "warnings": ["未声明 produce，产物记账将不可用"]}
   ```

**接入向导 UI（web 端 3 步）**：填仓库 → 看自检报告 → 确认登记。全程 ≥1 次真实动作校验（dry-run build）。

## 5. 分阶段实施

### P0：打通首个真实项目（1-2 天）

1. **GitIntakeService**（agent-infra）：
   - `cloneFromGitee(projectId, url, tokenRef)` → `git clone --no-checkout` → INTAKE 状态机
   - `importLocal(projectId, sourcePath)` → 校验 + 复制（保留 .git）
   - 虚拟线程异步 + 状态查询接口（clone 大仓库不能卡 HTTP）
2. **ProjectIntakeController**（gateway）：§4 的 4 个端点 + 参数校验（projectId 正则、URL http(s)）
3. **配方自检 RecipeCheckService**：§4 的 4 项检查 + 报告
4. **application.yml**：给 RY 项目配 `status: registered` 字段（ProjectsProperties 加字段），区分"配置预置"与"接入产出"

### P0 验收标准

- [ ] 用本仓库 `E:\CODE\Agent\agentscope-ruoyi` 本地导入为项目 `AGT`，跑通 `list_actions`（≥ backend_build/frontend_build 有配方）
- [ ] 从 Gitee clone 一个真实仓库（如 dromara/hutool）为项目 `HUT`，跑通 `ci_run verify`（verify 不部署，安全）
`ci_status` 到 SUCCEEDED 或明确 E-2xx/E-4xx
- [ ] 自检报告对无配方项目给出可操作警告
- [ ] 接入中途失败 → 状态 INTAKE_FAILED，重试可恢复

### P1：私有库与凭证（1 天）

1. `ProjectsProperties.ProjectDef` 加 `credentialRef` 字段；clone/fetch 告诉 git 用哪条凭证
2. 凭证落地方式（二选一，按部署形态）：
   - **文件凭证助手**：`git config credential.helper` + 平台写临时 askpass 脚本（token 只进内存/tmpfs）
   - **URL 内嵌**（仅演示）：`https://<token>@gitee.com/...` ——不落盘但会进进程列表（ps 可见），生产禁用
3. 单测：私有 URL + token 走通 clone（用本地 bare repo 模拟"远端"，不依赖真实私有库）

### P1 验收：私有 bare 仓库 clone 成功；token 不出现在日志（ProcessExecutor.redact 已有 token 形态脱敏）

### P2：接入向导前端（2 天）

1. web 端新增「项目接入」页：表单 → 提交 → 轮询状态 → 自检报告展示 → 确认
2. 项目列表页：接入产出与 yml 预置项目统一展示，`INTAKE_FAILED` 标红可重试
3. 下线确认卡片：二次确认 + 高危二次密码（复用 ConfirmToken 治理）

## 6. 遗留问题清单（需要决策/排期）

| # | 问题 | 影响 | 建议排期 |
|---|---|---|---|
| P1 | **项目存储是内存 + yml，重启丢接入** | 接入的项目重启即丢（yml 里的 RY 是预置，接入的新项目不在 yml） | **P1 前置**：`agent.projects` 只读预置 + 接入项目落 SQLite（单文件、零运维）；或干脆全部转 SQLite。推荐后者——InMemoryProjectRepository 已是接口隔离的，新增 SqliteProjectRepository 即可 |
| P2 | **clone 凭证传递** | 私有库 clone/fetch 无法鉴权 | P1 阶段一并做（见 P1 实施项 2） |
| P3 | **runs/ 无清理** | 磁盘无限增长 | P1 队尾加"清理保留最近 20 次 run"定时任务（简单：删除旧 runDir） |
| P4 | **git 安全扫描** | clone 进来的仓库是"不可信数据" | clone 后立即跑规约扫描？否——仓库内容仅被**确定性代码**执行（配方只取 argv，模型只读检索结果），风险可控；但 `ci/actions.yml` 是人写的命令，接入时向用户展示全文（自检报告已含）供 review |
| P4-b | **并发接入同一 projectId** | 重复 clone 竞态 | intake 状态机加 per-project 锁（synchronized/数据库唯一约束） |
| P5 | **Windows 长路径/中文路径** | clone 复制失败 | 复制时规范化 + 报错原样透出；长路径需注册表 LongPathsEnabled，文档记录 |
| P6 | **webhook 依赖 repo 已 clone** | clone 完成前 push 会 400 | 预期行为：向导完成前不配 webhook；文档写明顺序（先接入 → 再配 webhook） |
| P7 | **大仓库 clone 超时** | HTTP 请求挂死 | intake 用异步任务 + 状态轮询（P0 设计已含）；HTTP 只提交任务不等待 |
| P8 | **项目类型→能力集** | `type` 目前只是展示字段 | P2：按 v4 §1 的能力表真正装配工具（如 static 不给 db 工具）——当前平台无 db 工具，先记 backlog |
| P9 | **预置(yml)与接入(SQLite)两源合并** | 项目列表去重/优先级 | 配置预置只读 + 接入项落库；列表 = yml ∪ DB，id 冲突时 yml 优先并告警 |
| P10 | **磁盘配额** | 单项目吃满磁盘 | 台账字段（v4 §4 已设计）+ preflight 检查；P2+ |
| P11 | **首个真实业务项目从哪来** | demo 项目（hutool）只验平台，业务价值要真实项目 | 待用户决策：首个业务项目选哪个仓库 |

## 7. 决策点（需要用户确认）

1. **首个业务项目**：`RY` 预置的是 dromara/RuoYi-Vue-Plus（公开库，clone 即可验全链路）；
   若有自有业务项目（私有库），需走 P1 凭证方案。**建议先用 RuoYi-Vue-Plus 真实 clone 跑通 P0 验收**
   （ci_run verify 是纯构建+镜像，不部署，安全）。
2. **接入项目存储**：SQLite（推荐，单文件零运维）vs 继续扩展 yml（多项目后漂移难管）。
   建议直接 SQLite，InMemory 实现已接口隔离，替换成本低。
3. **工作区根**：开发机 `./data/workspaces`（默认）够用；服务器建议独立分区 `/opt/agent-workspaces`。
4. **本地导入的边界**：仅开发/演示场景；生产环境建议禁用 local 来源（配置开关 `agent.intake.allow-local: false`）。
5. **`ci/pipeline.yml` 模板生成**：接入自检发现无 pipeline.yml 时，平台生成模板文件写回 repo？
   ——**不建议自动写回用户仓库**（污染他人仓库）；改为把模板内容放进自检报告，用户复制提交。
