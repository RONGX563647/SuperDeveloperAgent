## 2. CI 抓到了什么（这是接入 CI 的直接收益）

### 2.1 分层违规：tools → governance

```
[tools.ChangeTools] 依赖 [governance.ChangeRegistry]
Layer 'Tools' may only access layers ['Domain'] —— violated 4 times
```

**这是真问题**，不是规则错。工具层直接依赖了治理实现，导致"工具能碰到治理内部"。

**修复**：在 domain 定义端口 `ChangeStore`，`governance.ChangeRegistry` 实现它，`ChangeTools` 只依赖端口。

> 同一模式此前已用于 `PipelineEngine`（原在 executor，现移入 `domain.port`）。
> **规律**：凡是"工具要用、实现又在别的层"的能力，一律在 domain 定端口——这不是形式主义，它直接决定了换实现时要不要改工具。

### 2.2 `Layer 'Gateway' is empty`（隐蔽的工程坑）

ArchUnit 扫不到 gateway 的任何类。原因：`spring-boot-maven-plugin` 的 `repackage` **把主 artifact 替换成 fat jar**，类被塞进 `BOOT-INF/classes/`，ArchUnit 的类导入器看不到。

**修复**：repackage 加 `<classifier>exec</classifier>`，主 artifact 保持普通 jar（21 KB），可执行包另生成（`-exec.jar`，53 MB）。

> 这个坑值得记住：**只要用 `mvn verify` 做架构检查，就不要让 repackage 覆盖主 jar**。否则架构规则会"静默通过"——不是守住了，是没检查。

### 2.3 测试代码里的 lambda 捕获

两个扫描器里 `scanned++` 被 lambda 捕获（非 effectively final）→ 编译失败。已改为 `final int scannedFiles = scanned`。

## 3. 当前脚手架的差距（按优先级）

### P0 —— 阻断"真的能用"

| # | 问题 | 位置 | 为什么是 P0 |
|---|---|---|---|
| 1 | **会话不持久化**：每次请求新建 `RealtimeContext`，无 state store | `ChatService` | 多轮对话无上下文，等于"一问一答"，追问就丢 |
| 2 | **身份是 `X-User-Id` 请求头** | `ChatController` / `ChangeController` | 可任意伪造；门禁与审计全部失效 |
| 3 | **确认令牌没有消费者**：没有 `apply` 接口 | — | 令牌签发后无处使用，治理链路是断的 |
| 4 | **高危变更 100% 被拒**（fail-closed 密码校验） | `FailClosedPasswordVerifier` | 安全但功能不可用，需要明确的"接账号体系"里程碑 |

### P1 —— 上线前必须补

| # | 问题 | 位置 | 说明 |
|---|---|---|---|
| 5 | SSE 无心跳、无 `Last-Event-ID` 续传 | `ChatController` | 规约 §3 明确要求；断线即丢事件 |
| 6 | 事件映射依赖内部类名（`AgentStartEvent`） | `AgentEventMapper` | AgentScope 升级即断前端；应映射为稳定枚举 |
| 7 | `changeId` 由前端**正则从文本提取** | `web/src/api/chat.ts` | 模型没原样输出就丢失；应后端发专用 SSE 事件 |
| 8 | 审计只写日志，无落库 | 全局 | 等保要求"可追溯"，日志不算审计表 |
| 9 | 无配额/限流 | 全局 | 一个用户可打满模型账单 |
| 10 | `ChangeRegistry` 无 TTL | `ChangeRegistry` | 变更单永久驻留内存 |
| 11 | 上游错误原样回传 | `ChatController#safeMessage` | 仍含 provider 的 message（可能带 baseUrl/模型名），应映射为分类错误码 |

### P2 —— 工程质量

| # | 问题 | 说明 |
|---|---|---|
| 12 | `Toolkit` 共享可变 | 将来按环境切换 `updateToolGroups` 会有并发问题；应按会话 `copy()` |
| 13 | 前端 SSE 解析未处理 `\r\n`、无重连 | `web/src/api/chat.ts` |
| 14 | 检查器缺 fixture 自测 | 正则写错无人知（见 spec-checks/README 已知限制） |
| 15 | 无端到端测试 | 「提单 → 定位 → PR」链路没有任何自动化验证 |
| 16 | domain 层无单测 | 目前只有 governance 有测试；`PlanHasher` / `Project.allowsPort` 值得补 |

## 4. 建议的下一步顺序

```
① 会话持久化（AgentStateStore 内存实现 → 之后换 MySQL）   ← 解锁多轮
② 账号体系（替换 X-User-Id）                              ← 解锁门禁与审计
③ apply 接口 + 执行器（先接 Noop，验证令牌闭环）          ← 解锁变更执行
④ SSE 心跳 + 续传 + 专用 change 事件                       ← 解锁体验与可靠性
⑤ mvn/npm 两个 stage 真实现                                ← 解锁真实构建
```

**理由**：①②③ 是"链路能不能跑通"的问题，④⑤ 是"跑起来好不好用"的问题。先闭环再优化。

## 5. 一条经验

接入 CI 之后，**两小时内被自己的规则抓到两次**（分层违规 + 静默失效的架构检查），两次都不是笔误，而是设计/构建配置的问题。

如果等到写了 50 个类再接，这两处的修复成本会高一个量级——`Layer 'Gateway' is empty` 这种"看起来通过其实没检查"的状态尤其危险：**它给你一种安全的错觉**。

> 结论：**规约检查要在写第一行业务代码之前接入**，而不是在"差不多完成"时补。
